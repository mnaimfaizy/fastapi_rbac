# S3

- **Id:** `s3`
- **Support Level:** `documented`. No run has uploaded to an S3-compatible bucket yet, and nothing below has been run against a real store: the signer is tested against AWS's published SigV4 vectors and the adapter against a fake store only. The first run that uploads to one moves it, citing its Activity Log.
- **Facts from:** the Amazon S3 API reference (`ListObjectsV2`, `GetObject`, `PutObject` with `If-None-Match`, `HeadBucket`, `GetBucketLifecycleConfiguration`) and AWS's Signature Version 4 documentation and test suite, read on 2026-11-25.

There is no CLI: `records.mjs` signs each request itself, with SigV4 from `node:crypto`, and sends it with `fetch`. `<endpoint>`, `<bucket>` and `<region>` are the config's `records.sink` keys of those names ([CONFIG.md](../CONFIG.md#records)). Requests are path-style, `<endpoint>/<bucket>/<key>`, which every S3-compatible store accepts. `<key>` is `records/<host>/<owner>/<repo>/<login>/<run-id>.json`, every segment lowercased.

## Access

- **Credentials** come only from two environment variables, `ORCHESTRATE_S3_ACCESS_KEY_ID` and `ORCHESTRATE_S3_SECRET_ACCESS_KEY`. They are never read from the config, a file or another variable (not `AWS_*`), and a value in the config that looks like a secret is a problem. Without both, nothing is uploaded and the dashboard shows one warning.
- **The writer** needs `s3:PutObject` and `s3:GetObject` on `records/*` in the bucket, plus `s3:ListBucket` (the privacy check needs to reach the bucket). The upload writes one new object per run and never changes or deletes one.
- **The reader** (the dashboard) needs `s3:ListBucket` and `s3:GetObject` on `records/`, and nothing more: it never writes, so it can be given to someone who may only look. With `ListBucket` limited to the prefix `records/<host>/<owner>/<repo>/`, the dashboard shows that repository only.
- **Raw run folders** (`records.raw.sink`) need more from the writer, and only for that sink: `s3:PutObject` and `s3:GetObject` on `raw/*`, `s3:ListBucket` for the privacy check, and **`s3:GetLifecycleConfiguration`** on the bucket, since the upload reads the lifecycle first. They never need `s3:PutLifecycleConfiguration`: the skill never writes bucket configuration, and a key without it cannot. The bucket owner sets a rule that expires `raw/` (about 30 days), and the key can be limited to `raw/<host>/<owner>/<repo>/` for one repository.
- Keep the key pair scoped to one bucket. Whoever holds it can do what its policy allows.

## Operations

### `visibility`

```text
HEAD <endpoint>/<bucket>                                  signed
GET  <endpoint>/<bucket>?list-type=2&max-keys=1           not signed
```

S3-compatible stores have no one field that says "private", so the check is the one a stranger would make. The signed `HEAD` must answer `200` (the bucket exists and the key works). The unsigned listing must be refused (`401` or `403`): a `200` means anyone can list the bucket, and the bucket is refused as `public`, with no override. Anything else, or an unreachable bucket, is refused as unreadable. Run before every read and write. The dashboard goes on reading when the answer is only "unknown" (a reader limited to one prefix cannot `HEAD` the bucket), with a warning that privacy could not be checked; the upload never does.

This does not see a public ACL or policy on a single object, or one that allows only `GetObject`. Turn on the provider's block-public-access setting for the bucket.

### `access`

S3 lists no one who can read a bucket, so there is no count: the disclosure leaves it out.

### `read`

```text
GET <endpoint>/<bucket>/<key>                             signed
```

The object's bytes. A `404` means the path is not there yet; any other failure stops the upload.

### `create`

```text
PUT <endpoint>/<bucket>/<key>                             signed, If-None-Match: *, Content-Type: application/json
```

The record's exact bytes. `If-None-Match: *` makes a store that supports conditional writes refuse an overwrite on its own (`412`, read as "already there"). A store that ignores it is covered by the read-first rule below, which every sink follows. A `409` is retried the same way: the path is read again, and identical bytes there mean the upload is done.

### `list`

```text
GET <endpoint>/<bucket>?list-type=2&prefix=records/&encoding-type=url[&continuation-token=<t>]   signed
```

`ListObjectsV2`, paginated: pages are followed while `IsTruncated` is `true`, by `NextContinuationToken`. Used by the dashboard, which lists `records/`, reads only the paths its cache lacks (`read`, above), and checks `visibility` first. A refused list of `records/` is retried once with the current repository's prefix, `records/<host>/<owner>/<repo>/`, and the page says it read only that: it shows nothing about other repositories. A bucket that cannot be read is one warning on the page, not a failure.

### `lifecycle`

```text
GET <endpoint>/<bucket>?lifecycle                         signed
```

The bucket's lifecycle rules, as the store's XML. Not used by the Run Record upload. Raw-folder upload reads it before it puts anything, and uploads only when an **enabled** rule expires **all** of `raw/` by age: `<Expiration><Days>`, with no prefix, a prefix `raw/` starts with, or `raw/` itself, written as the legacy `<Prefix>`, `<Filter><Prefix>` or `<Filter><And><Prefix>`. A rule with a tag or size filter, a date, a transition only, or a deeper prefix does not count; of several rules that do, the shortest days are quoted in the disclosure. A bucket with no lifecycle, one that cannot be read (`403` for a key without `s3:GetLifecycleConfiguration`, a failed request) or one with no such rule gets nothing uploaded. On a versioned bucket, `Expiration` only adds a delete marker, so the owner should also expire noncurrent versions of `raw/`; the skill does not check that. The skill never writes bucket configuration.

## The upload is create-only

- Identical bytes already at the path count as already uploaded, so repeating `--upload <run>` is safe.
- Different bytes at the path stop the upload: nothing is overwritten, and the clash is shown.
- A record that fails the safe-field check, or has no login, is never uploaded.

## Retention

Run Records are kept indefinitely unless the bucket says otherwise, and the disclosure says so. A shorter policy is the owner's own lifecycle rule on the `records/` prefix, set on the bucket and never by the skill. Anyone who can read the bucket's `records/` can read every record in it.

## Raw run folders

`records.raw.sink` names the bucket raw run folders go to. It is `s3` only, because only a bucket can expire an object by its own rule: a git sink cannot, and a raw folder may quote private issue text, command output and file contents. The upload (`records.mjs upload-raw <run>`) writes one object per file under `raw/<host>/<owner>/<repo>/<login>/<run-id>/<path>`, every namespace segment lowercased, create-only like the record, to a bucket that answers a signed request and refuses an unsigned listing. It sends text files only: a file that is not UTF-8 stops the upload before anything is put, and a link is never followed. It can share the bucket with the Run Record sink. The disclosure line, and the yes it needs at every close-out, are in [RUN.md](../RUN.md#uploading-the-raw-run-folder).

## Other storage

Any store that speaks the S3 API with SigV4 and path-style requests may work as an `s3` sink. These are **untested hints**, not promises: set `endpoint` and `region` as the provider's docs say.

- **AWS S3**: [S3 API reference](https://docs.aws.amazon.com/AmazonS3/latest/API/Welcome.html). Endpoint `https://s3.<region>.amazonaws.com`; lifecycle rules: [expiring objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html).
- **Cloudflare R2**: [S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/). Endpoint `https://<account>.r2.cloudflarestorage.com`, region `auto`.
- **Google Cloud Storage with HMAC keys**: [HMAC keys](https://cloud.google.com/storage/docs/authentication/hmackeys) on the XML API, endpoint `https://storage.googleapis.com`. Whether its signing is exactly SigV4 is not confirmed here.
- **Backblaze B2**: [S3-compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api).
- **MinIO**: [MinIO docs](https://min.io/docs/minio/linux/index.html), for a store you run yourself; `http` is accepted only for `localhost`.
- **Wasabi**: [Wasabi docs](https://docs.wasabi.com/).
- **DigitalOcean Spaces**: [S3 compatibility](https://docs.digitalocean.com/products/spaces/reference/s3-compatibility/).

**Not sinks today:** Azure Blob (it does not speak the S3 API), Bitbucket, Gitea and Forgejo. Use `github`, `gitlab` or `s3`.

## Moving to a new sink

Copy `records/` to the new sink under the same paths, and point `records.sink` at it. Create-only makes a repeated copy safe: an object that is already there is left as it is. For another bucket, any S3 copy tool does it, for example `rclone copy old:<old-bucket>/records new:<new-bucket>/records --immutable`. A record carries its namespace in its path, so nothing is renamed, and the dashboard reads the new sink's `records/` the same way. It shows only the namespaces in the one sink the repository reads.

## Check before use

- No upload has run against a real store yet: the signed requests, the `If-None-Match` write, and the `ListObjectsV2` XML are read from AWS's documentation and exercised in tests against a fake store only.
- Whether the privacy check is enough: it sees a bucket that lists to a stranger, not a public object ACL.
- Whether each provider in "Other storage" accepts path-style requests, `If-None-Match: *` and `encoding-type=url`: none was tried.
