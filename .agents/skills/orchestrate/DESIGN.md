# Orchestrate design

Why the skill is shaped the way it is. The skill carries this file so its rules keep their reasons in any repository it is copied into. Load it when changing the skill, or when a rule in [SKILL.md](SKILL.md), [SPEC.md](SPEC.md), [TEAM.md](TEAM.md), [BRIEF.md](BRIEF.md), [RUN.md](RUN.md), [HARNESSES.md](HARNESSES.md), [TRACKERS.md](TRACKERS.md), [SINKS.md](SINKS.md) and the files under [sinks/](sinks/), or [CONFIG.md](CONFIG.md) needs its reason.

## Glossary

These are word for word the definitions in Agent-kit's root glossary, where a contract test keeps the two the same.

**Chief of Staff**: The session that runs `orchestrate`: it analyses the work, proposes the Dispatch Plan, hands out each Delegation, relays every Decision Request (or, in an autonomous run, makes a Ruling on those it may) and verifies every report, and never does a Delegation's work or merges.

**Delegation**: One piece of a run, an issue to build, an issue to analyse, or a pull request head to QA, handed to one Executor with one brief.

**Executor**: What carries out a Delegation: a Live Session, a headless run, or a sub-agent in the Chief of Staff's own session.

**Harness**: The agent product an agent run happens in (Claude Code desktop, Claude Code CLI, Cursor, Codex CLI, Gemini CLI and the like), which decides how a run starts without a human, what it may touch, and how one session can start, message and wait for another; two versions of one product that behave differently are two harnesses.

**Support Level**: How far `orchestrate` has been proven on a harness, a tracker or a sink: verified (a full run passed, or for a sink, a run uploaded to it and read it back), tried (a run happened, with known gaps) or documented (built from its documentation alone). A Stage's level belongs to the harness and Stage pair, so one harness holds a different level for each Stage.

**Live Session**: A separate agent session the human can open, read and talk to while it works; always written in full, because a Session is a signed-in identity in a QA scenario.

**Brief Contract**: The eight items every Delegation's brief carries: what to read first, the goal and what done means, phases with explicit stop points, scope fences, the repository's command routes, the rules for writes, the Decision Request form, and the Delegation's report and log files.

**Decision Request**: A question a Delegation, or a Factory task, cannot settle from its brief, raised to the human (through the Chief of Staff, or on the issue with `factory:needs-decision`) or, in an autonomous run, answered by a Ruling; self-contained, with options, evidence and a recommendation.

**Pending Message**: Text the Chief of Staff has decided to send to an Executor (an answer, a Ruling, a nudge, a send-back, a merge order) that its harness cannot deliver until that Executor's run has ended.

**Ruling**: A Decision Request the Chief of Staff answers itself in an autonomous run, because the human handed it that kind at "go" and the evidence it cites picks one option; it stands until the Ruling Review.

**Ruling Ledger**: The ordered list of every Ruling in a run, each with its question, options, choice and evidence, kept in the run folder for the Ruling Review.

**Ruling Review**: The human's pass over a run's Ruling Ledger, in which each Ruling ends upheld or overturned; overturning one sends every Ruling that cited it back for review.

**QA held for you**: In an approved-QA run, the list, right after the Ruling Review, of the QA questions the human keeps, each with its row, evidence and options; not Rulings, so outside the Ruling Ledger, and a row is Ready to Merge once they are answered.

**Parked QA session**: In an approved-QA run on Claude Code desktop, a Live Session for QA started at the `go` turn on a brief with no head yet; it idles until the Chief of Staff messages it the head, and runs a re-QA in the same session.

**Scoped QA Delegation**: A QA Delegation (`d<issue>-qa<k>`) started when the human picks a new QA Delegation for scenarios left for a person; it runs only those listed scenarios on the same head and delivered QA Plan, on an Executor with the missing driver, and merges its rows into that head's one QA Report with provenance.

**Dispatch Plan**: The one table the Chief of Staff shows before any Delegation starts, giving each one's scope, Executor, model and wave, with the kinds of routine write the human may approve; one "go" approves it whole.

**Activity Log**: An append-only record of what was done in a run and why, kept by the Chief of Staff and by each Delegation in the run folder.

**Heartbeat**: A check on every Delegation the run waits on that comes again at a set interval, whatever happened since the last one, so that a run never waits on one signal alone.

**Foreground watch**: The Heartbeat on a harness with nothing to schedule it: the Chief of Staff keeps its turn open, waiting for a change in any Delegation or for a time cap, then waits again.

**Run Summary**: The account of a finished run, offered after the human merges, for the issue that groups the run's work.

**Run Record**: The structured, machine-readable account of one run (an `orchestrate` run, or one Stage run of a Factory task, on either Factory engine), written at close-out and holding only fields that are safe to publish (counts, ids, durations, outcomes, and each Human step with its kind and cause), never quoted issue text or command output; what a Consumer may keep or upload once the raw run folder is gone.

**Run Event**: One timestamped, structured entry for a single step of a run (a spawn, a human step, a land, a review, a CI result), written as it happens by whoever did it; the Run Record is derived from a run's Run Events.

**Human step**: One touch from the human in a run (one answer, one click or one typed command), listing the Decision Requests it covered, recorded in the Run Record with its kind and a `cause` from a fixed list, each cause avoidable or by design.

**Sink**: A store off the machine that a Consumer has configured to receive Run Records, or opted-in raw run folders; one Sink may serve many repositories, each writing only into its own namespace.

**Ready to Merge**: A Delegation whose CI is green, whose review is settled, whose QA requirement is met on its current head, whose Rulings are upheld, and whose branch merges cleanly into the default branch as it now is, and is not behind it where the repository requires branches to be up to date, unless the human chose to merge it as it is; the only Delegations the closing list names.

**Team Run**: A spec run started with `--team`, in which each teammate runs their own Chief of Staff over the spec's tickets assigned to them alone, beside the others, and every one of them reads one Shared Board. One per teammate; a spec's Team Runs are read together on the Shared Board or the Run Record dashboard.

**Shared Board**: The board of a Team Run on the issue tracker: one row comment on each spec ticket, written only by its current assignee's Chief of Staff, and one state label mirroring its state; a published projection of each teammate's own run folder, never a store.

## A core plus a config

The rules of running work through other sessions (the roles, the board, the Brief Contract, the loop, the authority limits) hold in any repository. The routes do not: one repository commits through a skill, another through a hook, a third by hand; one re-gates with a test suite, another has none. So the skill is a core that names no repository command, skill, label or path, and a config file that names them all. A rule in the core never has to be read around a repository's habits, and a repository adopts the skill by writing a file, not by editing it.

## The Chief of Staff never does a Delegation's work

A session that both builds and verifies a piece of work has a reason to believe its own report. Keeping the Chief of Staff to planning, delegating, relaying and checking means every report is read by someone who did not write it. It also keeps the Chief of Staff's context free for the whole run: a session deep in one Delegation's code loses track of the others. The rule holds most on a harness with no way to start another agent, where the easy path is to do the work in the same session. It covers QA work for the same reason: the Chief of Staff never starts the QA Stack, drives a scenario on any surface, runs the QA drivers (`web.mjs`, `http.mjs`, `storyboard.mjs`, `mp4.mjs`), or writes or edits a QA Report or its QA Artifacts, with no override even if the human asks directly or insists.

## Authority

Merging, force-pushing, changing repository settings, and destroying a branch, worktree or checkpoint are the actions that cannot be taken back, or that change what other people see. They need the human's yes, one action at a time, because a run is long and a yes given early is easily stretched over work it was never about.

A Delegation may push its own branch, open its own pull request and reply on its own review because that is the work it was given, and its pull request is visibly the agent's. Any other write as the human (a comment on an issue, a new issue, a label, a closed issue) speaks for them in a place others read as theirs. So it is drafted and raised. Routine kinds can be approved once in the Dispatch Plan, because asking about every label change would bury the questions that matter.

## One plan, one go

The human approves scope, Executor, model and wave for every Delegation in one table, because that is the decision that commits the run's cost and the human's attention. A change to any row is a new plan, shown again: a "go" given to one plan is not a "go" to another. Adding `go` to the invocation skips the wait for a run the human already trusts, but never skips a Decision Request that analysis raised.

## Readiness by triage role

An issue built before its design is settled produces a pull request that answers the wrong question, and the review then argues about the design. So readiness comes from the triage role the repository already gives the issue, and only `ready-for-agent` is built. Every other role is analysed, listed, or skipped. The skill speaks in the five canonical roles and reads the labels from the repository's own mapping, because label strings differ between repositories and the mapping is already written down; restating it in the skill would make a second copy to drift.

## Waves, overlaps and blockers

Two Delegations that change the same files in parallel produce two branches that conflict, and the second to merge must redo work. Two that hold the same shared resource (a database, a port) break each other's runs in ways that look like flaky tests. So neither shares a wave. A Delegation that waits for another, by overlap or by a blocking issue, starts only once that one is merged, so it is built on the code it will merge into. The limit on concurrent building Delegations exists because each one asks for the human's attention, and attention does not scale with sessions.

## The Brief Contract

An Executor knows only its brief. Each of the eight items closes a gap a Delegation would otherwise fill by guessing: what to read, what done means, where to stop, what not to touch, how this repository commits and opens pull requests, what it may write as the human, how to ask, and where to put its report. Explicit stop points let the Chief of Staff check work at known places rather than at the end. Every building brief ends with a review of its own diff before the final commit, because a finding fixed before the pull request costs a commit, and one found after costs a round of review.

## Decision Requests are self-contained

The human answering a question is often away from the Delegation that asked it, and may answer from a phone. A question that says "see above" makes them open the session, read its context and reconstruct the choice. So a Decision Request carries its own context, options, evidence and a recommendation: the human can answer from it alone, and the recommendation means the answer can be one word. The answer is recorded where a reviewer of the pull request will see it, because a reviewer who cannot see why the work went one way will ask the same question again.

## Rulings, under review

A long run with the human away stalls on every question, and most of the questions are ones the evidence already answers: how to build within a settled issue, which branch merges first, whether a QA FAIL is the change or the stack. So in a run the human starts with `go autonomous`, the Chief of Staff answers those itself, as Rulings, and the human reviews each one before anything merges.

The line between what it may rule on and what stays the human's is reversibility. A Ruling's result is a commit on an unmerged branch, which an overturn undoes with another commit. A wider scope fence, an accepted FAIL, a write in the human's name, or a choice among an analysis Delegation's options cannot be taken back by the review, or changes what the human approved at "go". So those still wait for the human, and only their own Delegation waits with them.

A Ruling needs evidence that picks one option, cited so that it can still be checked after the branch has moved, because the review happens after the run and "it seemed reasonable" cannot be reviewed. The Ruling Review comes before Ready to Merge, because an overturn before the merge costs a commit, and after it a new issue. A Ruling that cited an overturned one is reviewed again, not overturned with it, because it may stand on other evidence. Authority is not ticked per kind, as routine writes are: one fixed split keeps the plan to one checklist until a run shows it needs more.

## Verify every report

A Delegation's report says what it believes it did. A branch that was never pushed, a check that is still running, a review comment marked handled that was not: each reads as done in a report and is not. So the Chief of Staff checks every claim against git, the tracker and CI before it tells the human anything, and re-gates in its own worktree, so a dirty working copy in the Delegation's cannot make a command pass.

## Stalls and crashes

A Delegation that has stopped making progress looks the same as one doing slow work, from outside. The Chief of Staff reads its Activity Log and branch before deciding which it is, nudges once, and raises it to the human if the nudge does not help: one nudge catches a Delegation waiting on something it forgot to ask for, and a second would only repeat it. A crashed Delegation's branch holds work no one else has, so it is kept as the handoff, and nothing about it is destroyed without the human's yes.

## Conflicts before the merge order

Two branches can each merge cleanly into the default branch and still conflict with each other. A merge order found only by merging would leave the human mid-sequence with a conflict to resolve. So the Chief of Staff test-merges the finished branches in the proposed order, without touching any checkout, and changes the order, or has one branch merge the default branch after the other lands, before it hands the order over. A merge, not a rebase: rebasing a pushed branch needs a force-push.

## QA on the head that merges

The first real run of this skill reached "almost Ready to Merge" with no QA at all: the readiness check only asked whether a QA Report existed, and nothing in the run made one. So QA is a stage of the run, not a precondition someone else meets.

It comes last, after review is settled, CI is green and the branch merges cleanly, because each of those can move the head, and a QA result is about one commit. A review fix that lands after QA leaves a report about code that will not merge. So any push voids the result, and the new head is QA'd again. Conflicts are found before QA for the same reason: the merge commit that resolves one is a new head.

QA is a Delegation of its own, not the building Delegation's last phase. A session that built a change has a reason to believe it works, as the Chief of Staff would about work it built itself. A separate Executor, in a working copy detached at the verified head, tests what the pull request holds, not what the builder's worktree holds. The QA skills (`qa-plan` and `manual-qa`) are named by the core, not the config, because the core reads what they produce: the plan's Head and the report's rows. A different skill would produce something the core cannot check.

Outside an autonomous run, those skills are invoked only by a person, and stay so: their rules ("the person has seen the draft", "post only on a yes") assume one, and making them model-invocable would undo that for every user, not only in a run. So a QA Delegation's session is sent each skill as a message where the harness runs that as the user's own invocation, and otherwise the human types it there, as the Dispatch Plan says up front, with the exact command. In an autonomous run the human has already handed the Chief of Staff the questions those rules wait on, so typing each command would keep a person at every QA step of a run meant to go on without them. There the QA brief carries each skill's `SKILL.md`, as the CI reviewer's brief carries `code-review`, and each skill's own "Run from an autonomous brief" section says what replaces each wait, since only the skill knows where it waits. A hosted (`url`) target runs from its brief too: its host is typed by the human in the Dispatch Plan and relayed with a provenance line, and a role's values are never collected, so a brief carries what it needs. Only plain `go` stays on the typed route.

The readiness question is asked once, in the Dispatch Plan, because otherwise each QA session asks it: in one run, the human answered it six times. Its answers are facts about the repository, which only the human knows, so they are never a Ruling. They hold for the base branch they were given for, since an answer can name the base the plan is composed against. The QA Plan's delivery is always a Decision Request carrying the draft (in approved QA, answered by a Ruling, or held), because the plan is a judgement about what CI does not prove, and the human is the one to agree with it before anyone runs it. Posting the report can be approved once for the run, because by then the judgement has been made and the report only records it.

A FAIL goes to the human, never straight back to the builder (in an autonomous run, a Ruling may send it back, and accepting it stays the human's): a FAIL can be the QA Stack, not the change, which is why QA Plans list red herrings. A scenario left for a person is never run by the Chief of Staff: the human either sends those scenarios to a new scoped QA Delegation (`d<issue>-qa<k>`) on an Executor that has the missing driver (whose rows merge into the head's one QA Report with provenance), runs them themselves, waives them, or (with QA approved) runs them after merge. The QA Stack is one per machine, with fixed names and ports, so it has one holder at a time whether or not the config names it.

## QA asks nothing mid-run

Handing a run to the Chief of Staff with `go autonomous` is a decision about how much to trust its rulings. QA is another one, since it spends a browser, a stack and time, so approving it is a separate yes in the Dispatch Plan, asked only when the config proposes QA rows and open to striking single rows. A run can be autonomous without QA, and a "no" is a real choice: those rows are Ready to Merge without it, and the board and close-out say so, so the decision is visible later.

Once QA is approved (approved QA), a QA session is never `waiting` on the human, because one that stops to ask makes the run attended again, and in the run this came from the human answered the readiness question six times. So every question QA would ask is settled before the session starts or not by the human at all: facts only they know are asked once in the Dispatch Plan, including the run's needs, the `working_dir` check and an optional local address, since a missing address would otherwise be a mid-run question; what the evidence settles is a Ruling, under the same bar as any other; and the rest is held for close-out. Held is not queued: a queued question stops its Delegation, and a held one lets the run go on and be answered in one sitting, with each item's row, evidence and options listed together. The list sits outside the Ruling Ledger because those items are not Rulings: nobody decided them, and the Ledger is the record of what the Chief of Staff decided. What the human keeps is what they would regret having decided for them: accepting a FAIL, waiving a scenario, a judgment call on wording.

A hosted target runs with no human mid-run because the safeguard was never where the human types: it is that a person, and not a file, a plan or an agent, gives the host. So each host is typed in the Dispatch Plan, in the human's reply, where `host` checks it and only `hosted` goes ahead, and a host the human did not type, or that it refused, is held with its scenarios before "go". The seeder is asked per environment for the same reason: a "yes" lets the QA session print the role values itself, so no secret passes through the Chief of Staff, a file or a brief, and a "no" holds the scenarios that sign in there rather than asking for values. A host reaches the QA session only through its brief, with a provenance line, is never saved to the config, and is deleted at close-out, so a later run or reader cannot take it for a standing confirmation. The session checks it again before any sign-in, and a refusal holds only its scenarios: held, never typed, since a typed route mid-run would put the human back in the loop the run was approved to leave (ADR 0032).

A QA claim is checked by its header, not by the session's word. The posted comment's first line is a fixed form a program reads, with the commit it is for and the counts of what was left for a person and deferred, so the Chief of Staff can check a claim against git and the QA Report in one command (`report.mjs summary`) instead of trusting a sentence. A header that does not parse, names another commit, or disagrees with the report counts as no report: a QA result is about one commit, and the old way (a Chief of Staff reading prose) let a result for an older head stand. The Places are shown in the Dispatch Plan for the same reason as the readiness answers: they are facts about the repository (where a person checks each item, and which places hold a merge), and only the human knows them, so they are asked once, never mid-run. Uploads are one opt-in, not a question per file: a per-file question is a mid-run question, and "approved QA is never `waiting`" would be false the first time a run produced evidence. The yes is about one thing, publishing to a release with the repository's visibility in front of the human, and the eligibility refusals stay in code, so the yes cannot widen what may leave the machine; a failed run's media is never uploaded, since it may show the failure's state. The stale edit is skipped because the header already names its commit (an older comment is visibly stale) and a re-QA's post replaces the comment; the close-out lists a comment left standing because posting was not approved, so the human sees it.

A QA session on Claude Code desktop starts parked, at the `go` turn, because that is the one turn that always allows `start_session`: the human's own words there authorize it, while a turn the app starts (a heartbeat, a turn-end) can only propose a card, and a card needs a click, which an unattended run does not have. So the sessions start before any head exists, on a brief written without `<head>`, and are messaged the head when step 9 has one. A re-QA reuses the same session for the same reason, since a new session mid-run would be a card. What the human gives up is a sidebar row for each QA row, idle from `go` until its head is verified, and a session that may not survive the wait: an archived, crashed or dropped one holds its row for close-out rather than turning into a card. The headless alternative, `executors.qa: claude-code-cli`, starts with no click at any turn, and costs what a session's tools give: the human cannot watch it, it has no built-in browser, and it runs with `--permission-mode auto`.

A Review box is a promise only reading can check, and a tick is a person's sign-off. A box that names words a file must carry is a copy check, so a Ruling can make it on evidence: the session quotes the file at the pinned head, and the Chief of Staff reads the source at that commit itself, since a session's quote alone is its own claim. A box whose words the file lacks is a FAIL, because a missing promise is to be fixed, not waved through. Even a "holds" Ruling never ticks the box. No agent ever ticks one, so the tick, and what it means, stay with a person. The ruled box is recorded as `(checked under R<n>)`, so a reader can find which Ruling checked it. Agent-kit's own record of this decision is ADR 0032, which supersedes ADR 0013.

## The scope fence binds every change

In the first run, a fix for a review finding, relayed by an automated fixer, was committed outside the Delegation's scope fence without a question, and was found only by diffing the new head. A fence that holds for the Delegation's own plan but not for what a reviewer asks for is no fence: reviewers ask for exactly the changes nobody planned. So the fence covers every change on the branch, and step 7 checks the diff against it.

## Ready to Merge, and no further

The closing list means something only if every item on it can be merged now: green CI, a settled review, the QA the repository requires, and a clean merge into the default branch as it now is. The skill stops there and prints the merge order and, when the config names one, the merge command, because merging is the human's act: it is the point where the work becomes theirs, and a merge train that merges on their behalf takes that from them.

## The default branch, checked on the human's return

A row verified against the default branch can stop being Ready to Merge without anything in the run changing: a merge from outside the run, or the human's own merge of the row before it, moves the tip. Under a rule that requires branches to be up to date, the row is then behind, and GitHub will not merge it; without that rule, it may still merge into code it was never tested with. In the first run that met this, the default branch moved three times while rows waited, and the Chief of Staff caught each case by hand. So a row is checked against the tip as it is now, and the merge result is re-gated whenever the tip has moved, strict rule or not, because two changes that each pass can fail together.

The check runs when someone is about to act on the list: at close-out, on `--status`, on `--resume`, and when the human says they merged a pull request. It is not kept on a heartbeat. While only the human's merges are left, the tip moves when the human, or someone outside the run, merges, and a heartbeat would spend a turn every few minutes, for hours, finding nothing the human is not about to look at. Checking on the human's return catches every move that matters, since a stale row matters only when someone reads the list. For the same reason, when more than one row is listed, the merge order asks the human to merge one at a time and say so, so the next row is checked against the tip their merge made: waiting to see a row `BEHIND` first would mean the first merge is already done.

Whether the repository requires branches to be up to date is read from the pull request's `mergeStateStatus`, not from its rulesets or branch protection: GitHub has already applied whichever of them holds, and reading them would mean knowing every way a rule can be set. A behind row gets two options, and the cheaper one, merging as it is with the admin bypass, stays the human's even in an autonomous run, because it sets a repository rule aside.

## The run folder

A run outlives a session: usage limits end it, laptops close, and a run with blockers pauses for merges. So everything the run knows is in files in a gitignored folder: the board, both kinds of Activity Log, each brief and each report. `--resume` rebuilds the run from them, and checks every Delegation against the source first, because a board written before an interruption may be out of date. The board is rewritten whole and renamed into place, so an interruption mid-write leaves the last whole board. The folder is gitignored because briefs and logs quote issue text and command output the human has not chosen to publish. When it is not ignored yet, the skill offers to add it to `.gitignore` rather than write there first: adding the line is a change to the repository, so it waits for the human's yes, and the human commits it.

## Four verbs, three tiers

Harnesses differ in how one agent starts another: some start sessions the human can open, some start background runs to poll, some cannot start one at all. The skill body speaks only of `spawn`, `message`, `await` and `report`, and HARNESSES.md says how each works on each harness, so the body does not change when a harness does. Reports travel as files on every harness, so the verbs only carry signals. And no signal is trusted alone. A harness's wake-up is a turn-end, not a finished report: it comes at most once per turn, which can be before the report is final. It does not come for a Delegation stuck on a prompt, or for a wait on CI that ends with nothing found. In one run, the Chief of Staff sat idle in each of those ways while the human was away. So `await` pairs the harness's event with a heartbeat that re-arms itself, every wake-up is read as "something may have changed", and a report says whether it is final. The cost is a short turn every few minutes; the alternative is a run that stops without anyone knowing. Facts about a harness are dated and marked when unconfirmed, because a harness changes faster than the skill, and a guessed flag fails at the worst moment of a run.

On harnesses that use the foreground watch, the watch shell loop stays strictly read-only (inspection and stdout only) and is fenced by a monotonic generation id in `watch.gen` (with optional `watch.pid` cleanup). A watch left running past a turn end or an interruption cannot safely write `activity.md`, `board.md`, or `events.jsonl` once a new watch or `--resume` has started, and any late watch output whose generation id does not match current `watch.gen` is dropped without acting. For the same reason, `activity.md` is prose context and baseline only: `--resume` and heartbeat checks verify `decisions.md`, `report.md`, and git/PR/CI source rather than acting on unattributed Activity Log lines.

Each harness has a file of its own, and a run loads only the one it is on, so a run on one harness carries none of the others' facts. The run finds its harness, from the environment and its own tools, rather than trusting the config alone: the same repository is opened in one harness one day and another the next, so a config value goes stale, while a guess sends every Delegation down the wrong route. So the config may pin the harness, and a disagreement is a question, never a choice the run makes. Each harness carries a **Support Level** because "documented" and "proven" fail differently: the first Cursor run followed a harness description no run had tried, and invented what it lacked. Below `verified`, the human sees the level and the harness's limits before the "go", and a level rises only on a run's evidence. Executors may run on another harness because one harness's headless run can carry a run whose own harness cannot yet; it is not the default, because it needs a second CLI signed in and a second set of model names.

## The config reader

The skill imports only Node built-ins, and Node ships no YAML parser, so `config.mjs` reads JSON whole and YAML in a small documented subset. Anything outside the subset, any unknown key, any key written with no value, and any wrong shape is a **problem**, named with its line in either dialect, never a silent default: a typo in a route would otherwise send every Delegation down the default one, and nothing would say so. A document the brief sends every Delegation to must be there, for the same reason. Missing values are asked for, not assumed, and the answers are kept in the run folder so a resumed run reads the same ones.

## Spec mode is a file of its own

Most runs are a set of issues, and an agent reads every line it loads. So spec mode lives in SPEC.md, loaded only for `--spec`, and a run on issues carries none of it.

A spec arrives in one of three shapes, and each is planned from what is already written. Tickets under a spec, with their blocking edges, are a breakdown the human has published and reviewed, so the waves follow the edges and nothing is re-planned. Phases in a spec's body are a breakdown too, but only in prose: they run in the order written, because that order is the only dependency the author stated, and a phase's own text is its spec, because rewriting it into a brief would be a second spec to drift from the first. Publishing the phases as tickets makes the tracker show the breakdown the run uses, but it is a set of new issues in the human's name, so it is drafted and asked for. A spec with neither has no breakdown at all, and inventing one would be building on an unsettled design: so it gets a Decision Request and no Delegations.

## Two landings

A spec's tickets can land two ways, and neither is right for every repository, so the plan asks, or the config says which.

**An integration branch** suits a spec whose parts only make sense together, or a repository that reviews a feature whole. Every ticket is built on the tickets before it without waiting for the human to merge, and the human reviews one pull request. Each ticket branch is cut from the integration branch so it is built on the work it lands into, and fast-forwarded back in plan order so the branch's history is the plan, and so a ticket that finished early never lands before the one it builds on. A fast-forward that is not one would mean rewriting a branch, so a ticket that no longer descends merges the integration branch first. The branch is re-gated at each fast-forward because two tickets that each pass can fail together, and finding that at the ticket that caused it is cheaper than finding it in the final pull request. The re-gate runs on the ticket's head before the branch moves: a fast-forward makes that commit the new head, so it is the same check, and a ticket that fails never enters the branch, so nothing has to be moved back, a resumed run can trust that every ticket in the branch passed, and a pushed branch never needs a force-push. The cost is that CI sees nothing until that pull request, so the re-gate commands are the only check on each ticket, and the review at the end is large.

**One pull request per ticket** suits a repository that reviews in small pieces, or a spec whose tickets stand alone. Each ticket is reviewed and merged on its own, with CI on each. A later wave waits until its blockers are merged, for the same reason a blocked issue does: it is built on the code it will merge into. The cost is the human's time between waves, which is why the run parks and continues with `--resume` instead of keeping the Chief of Staff's session open.

## The integration is reviewed whole

Each ticket's review sees only its own diff against its cut point, so it can find nothing that lives between tickets. In the spec #413 run, the first review of the integration pull request found two bugs where tickets met: one ticket's parser did not match a pattern another added, and one ticket's check ran before another's merge. It also found ten stale passages, in lines no ticket had changed, that still stated a rule the spec had replaced. No ticket's review could have seen either kind, and the pull request was already open, so finding them cost a whole fix round in public. So one review Delegation reads the whole integration diff before the pull request is drafted. A stale passage is a line nobody touched, so reading the diff cannot find it: the review searches the repository for the old wording of each rule the spec changes, and a list it must account for in full is its completion criterion, where "review the diff" has none. The same list is in each building brief whose ticket changes a rule, so the Delegation that makes the change is first to look for what it leaves behind.

## The re-gate and the landing are commands

Every landing took the same steps, and the Chief of Staff typed them each time: add a detached worktree under the run, run the six commands, filter their output, remove the worktree, compare the failing tests to five known baseline failures by eye, read the fence off `git diff --stat`, check that no worktree held the branch, and `update-ref`. A pipeline typed from memory drifts, and a comparison by eye is where a new failure that looks like a known one gets through, or a known one stops the landing. So the steps are `config.mjs regate` and `config.mjs land`, tested against real repositories. The known failures are listed in the config with a reason, so they are reviewed there once, and a fix removes its entry. A listed name is matched whole, and a command that fails with no test named, or counts more failures than it names, is never allowed: the list can only excuse a test it names. `regate` takes its commands from the Chief of Staff's own config, so a ticket cannot change what checks it. `land` moves the branch by `update-ref` with the old value alone, and never merges, rebases or pushes, so a landing can only be the fast-forward the plan describes, and every refusal names a cause the Chief of Staff relays instead of working around.

## The integration branch stays local

An integration branch holds unreviewed work from several Delegations. Pushed, it is public to everyone who can read the repository until someone deletes it, and a deleted branch can still have been fetched. Executors in worktrees of the same repository share its branches without a push, so most runs never need one. An Executor that works from a clone does, and that is the human's choice to make, knowing what becomes public, not the Chief of Staff's: so it is a Decision Request that says so, and the yes covers that branch only. Opening the final pull request pushes the branch too, so it is asked for in the same way.

## Team Run

A team that splits a spec's tickets wants each person to run their own, side by side, and to see where everyone's tickets stand. A single-person run cannot give that: its board lives in a gitignored folder on one machine. So a Team Run is federated. Each teammate runs their own Chief of Staff, on their own machine and harness, over the tickets assigned to them alone, and no session drives another person's machine. There is nothing to join, and the tracker's assignee is the only sign of whose ticket it is, because it is already where the team decides that. A Chief of Staff never sets it.

The Shared Board is one row comment per ticket, written only by the Chief of Staff of that ticket's current assignee, with a state label mirroring the row. Neither GitHub nor GitLab locks a comment, an issue body or a label against a second writer: the last write wins, with no error to the loser. A board in one place would lose rows silently whenever two teammates wrote within one read and write, so the board is cut so that no two teammates ever write the same value ([ADR 0014](https://github.com/mnaimfaizy/agent-kit/blob/main/docs/adr/0014-a-team-runs-shared-board-is-one-single-writer-row-per-ticket.md)).

The board is a projection of each teammate's run folder, not a store that replaces it. The run folder is gitignored because briefs and logs quote issue text and command output nobody chose to publish, and on a public repository the Shared Board is the open web. So a row carries only fields and text written for publication, and the run's state stays where `--resume` and verification already read it ([ADR 0015](https://github.com/mnaimfaizy/agent-kit/blob/main/docs/adr/0015-the-shared-board-is-a-published-projection-of-each-local-run-folder.md)). Writing it is one routine write, approved at "go" for the teammate's own tickets, and the plan says when the repository is public, so nobody publishes to the open web without seeing that first.

A Team Run lands one pull request per ticket. An integration branch would have to be pushed and shared between teammates to hold their work together, and a ticket that blocks a teammate's would have nowhere to land for them. A pull request per ticket gives each teammate's ticket its own merge, which is the one event every other teammate can read: a ticket blocked by a teammate's waits for that merge, as a blocked issue waits in any run.

A ticket with no assignee, or with two, is run by nobody. Guessing an owner would put two Chief of Staff sessions on one branch, or none on a ticket somebody thought was theirs, and the fix is one click on the tracker by the people who know.

The tracker is reached through a short list of operations, named in TRACKERS.md and each mapped in its own file under `trackers/`, as HARNESSES.md names the verbs and each harness has its file under `harnesses/`. Only the Team Run's parts speak of them; the rest of the skill stays bound to `gh`, since a tracker-neutral core is more than a Team Run needs. Detection reads the git remote's host because that is where the tickets live, and a pin that disagrees is a question: either could be the mistake, and a run on the wrong tracker reads the wrong tickets.

Like spec mode, the Team Run is a file of its own, TEAM.md, loaded only for a Team Run (`--team`, and `--status` or `--resume` of one) and for `--status --spec <n>`, so a single-person run reads none of it.

## Run Events and the Run Record

A run used to leave only a gitignored folder and a prose Activity Log with dates but no times. Hand-deriving records from two past runs (spec-344 needed the human 23 times, spec-253 65) showed that no duration, no wait on the human and no cause could be read from it, and that the list of human steps took judgement. So each step is written as a **Run Event** when it happens, with a time from the clock, by whoever took it: the Chief of Staff for its own steps and each Delegation for its own, because a Delegation's steps between the Chief of Staff's wake-ups are otherwise lost, and its start and end are only true if it writes them. The Run Record is derived from those events at close-out and never written by hand, so every run counts a step the same way.

A human step is one touch, listing the Decision Requests it covered, because a count of questions measures how many the Chief of Staff batched, not how often the human was needed. A wait is an open and a close sharing one id, so the time spent waiting is measured and a wait still open is visible. Every write carries an `actor`, since `gh` shows the same login for the human and for the Chief of Staff writing as the human, and a record that blurs them would call the Chief of Staff's writes the human's steps. The "why" is a `cause` from a curated list, each avoidable or by design, because prose cannot be counted, and a team improves the skill only on what it can count. Expected steps (the plan's approval, the merge, the close-out) are by design so that they never read as waste.

The Run Record holds only counts, ids, SHAs, issue and pull request numbers, times, durations, enum values and outcomes, so that it is safe to keep and to share. The rule is enforced by a check, not by care: every value has a type that cannot hold a sentence, and a field outside the schema is an error that names it, never silently stripped, because a stripped field is a record that quietly differs from the events it came from. The record is written to `<run_dir>/records/`, beside the run folders and not in one, so that pruning or deleting a run folder never deletes it. The Activity Log stays as the readable prose, and Run Events never leave the run folder on their own. `run-record/1` covers `orchestrate` runs (`run.kind` `tickets`, `spec` or `team`); a Stage's record is a later schema.

The records script is Portable, on Node built-ins and the tracker CLI, like the config reader, and has one CLI and one `main(argv, io)` seam. `io` injects the clock, the files root and a transport, so every later part of this work (a sink, pruning, the dashboard, the live board) extends one script and is tested the same way, with no network. The operator is read from the tracker CLI and overridden only by `ORCHESTRATE_OPERATOR`, so a committed config never names a person. Records start with the first run that writes events: a backfill would be built on guesses.

A Run Record is uploaded to a **Sink** only after a disclosure, and only to a private one. The disclosure says where the record goes, the exact path, what it holds, how many people can read the sink and how long it is kept, because uploading is the one step that moves a record off the machine, and the human should know what they are publishing before the first time and not discover it after. A run can approve the upload once, as a routine write in the Dispatch Plan, so it is not asked at every close-out; and "Not now" costs nothing, since `--upload <run>` uploads the same record later. The write is create-only: nothing in a sink is ever overwritten, so repeating an upload is safe and a clash is raised and never resolved silently. The sink's visibility is checked at every upload, with no override, because a private repository can be made public after it was chosen. One sink may serve many repositories: each writes into a namespace of its own (`records/<host>/<owner>/<repo>/<login>/`), so two repositories never collide, and the login in the path comes only from the tracker CLI or `ORCHESTRATE_OPERATOR`, so the committed config names no one. Each sink has a file of its own, mirroring the tracker files, that states the writer's access and the reader's, and its Support Level: `github` is `verified`, while `gitlab` and `s3` ship at Support Level `documented` until a run has uploaded to them and read the record back, and the Dispatch Plan and the close-out say so until one has. GitLab documents no create-only write, so that adapter reads the path before it creates it, and the same create-only rule above then holds on every sink. The `s3` sink is any S3-compatible bucket, signed with SigV4 from `node:crypto`: it has no list of readers, so the disclosure leaves the count out, its credentials come only from `ORCHESTRATE_S3_ACCESS_KEY_ID` and `ORCHESTRATE_S3_SECRET_ACCESS_KEY`, and a bucket is private when it answers a signed request and refuses an unsigned listing.

Pruning local run folders is opt-in and is the one setting that deletes data, so a run with no `prune.after_days` deletes nothing and setting the key is the consent. The close-out asks once, because the people most helped by pruning are the ones who never read the config: one question at 90 days turns it on, and the key is written only on a yes, so a "no" never edits a file the human did not choose to change. A "no" is remembered in a marker file beside the run folders on that machine, since the config is shared and the refusal is a personal choice. Only closed-out folders go, judged by their Run Record (derived at close-out, outside the run folder), so an open run is never mistaken for an old one, and the records the dashboard and sinks read are never touched.

A raw run folder is a different thing from the record, and is uploaded on different terms. It keeps what the record was built to leave out: issue text, command output, file contents. So it leaves the machine only when a Consumer sets `records.raw.sink`, only to an `s3` bucket, only after the bucket's own lifecycle rule is read and found to expire `raw/`, and only on a yes of its own at every close-out. It is `s3` only because only a bucket can delete an object on its own: a git sink keeps what it is given (the same reason the record's disclosure says a git sink cannot expire it). It is never a routine write, because a yes given once at "go", before the human knows what the folder will quote, is the wrong place for that consent, and an answer given for one run says nothing about the next. The skill reads the lifecycle and never writes it: that keeps its key to object read and write, and repositories that share a bucket cannot overwrite each other's rule. With no rule, or a lifecycle it cannot read, it uploads nothing, so a raw folder cannot be kept forever by mistake. The dashboard never reads it.

### The past-runs dashboard is a file on the reader's machine

`--dashboard` builds a static HTML file from the local records, instead of serving a page, because a file needs no server, no port and no hosting, works offline, and holds no credential: the data is read when it is built and inlined, so the browser never has anything to leak. The cost is that it does not update, so the page says when it was built and how to rebuild it. The command prints a `file://` link and never opens a browser, because harnesses differ in what they may launch.

The sink is read when the page is built, through the same adapter the upload writes with, so a sink type is written once and read by both, and the credential never reaches the page. Every path in a create-only sink is final, so a fetched record is cached forever, in a folder that mirrors the sink's paths, and a rebuild fetches only what is new: that is why there is no index file to trust or to keep in step. Namespaces come from paths alone for the same reason. An unreadable sink is a warning and not a failure, because the local records are still worth showing, and a sink turned public is read anyway, with a warning, because refusing to read would hide records the owner needs to see while fixing it. Where the local and the sink copy differ, the sink's wins, since it is the one the team sees.

Prose is kept out of it for the same reason Run Records hold none: a page that can be passed around should not carry what a record was built to leave out. `--local-logs` is the one way prose gets in, and it goes into a second file with a banner that says so, never into `dashboard.html`, so the file a person shares by habit is the safe one. Colour means `cause` and nothing else, so a reader learns one meaning for it, and states are grey so that an outcome is never mistaken for a reason. The page shell and the stylesheet are one module of their own, so the live board can use them without a second look.

People are shown by login, sorted by login, with no ranking, score or total, and no config key hides them. Anyone who can read the sink can read every raw record, so hiding names on the page would only pretend to protect them; the controls that are real are who uploads and who can read the sink, and the docs say so. Run counts and lengths are per run kind, because a one-issue run is not a five-ticket Team Run; only human steps per Delegation compare across kinds. A person is `(repository, login)`, and on _All repositories_ `(host, login)`, so one login on two forges stays two people, and there is no alias map to maintain. The Spec page reads a spec's Team Runs from the records alone and names the sink it read, because a teammate whose records are not in it looks the same as a teammate with no work: the page says what it cannot see, and never reads the tracker to guess.

### The live board is a file the page reloads, never hosted

The live board is `board.html`, written beside `board.md` each time the Chief of Staff rewrites it, instead of a server, because a file works in every harness, needs no port and no process that outlives a turn, and holds nothing the run folder does not. The cost is that it moves only as fast as the board is written, so the page reloads itself every 15 seconds and the Chief of Staff rewrites it with the board. A server on 127.0.0.1 is the optional second way: it pushes Run Events to the second, but it needs a process that harnesses do not all allow, so nothing depends on it.

The server uses Node built-ins alone. It reads the events files on a short timer rather than trusting file-system notifications, which differ between platforms, and sends events one way over Server-Sent Events, since the board is read-only. It listens on the loopback address, refuses a request made to any other name (so a web page cannot reach it through a DNS name it controls) and sends no CORS header. A page served over HTTP cannot send the browser to a file, so when the server stops the page says so and gives the file board's address, and reloads only while the server answers, so it never leaves the reader on an error page. `/dashboard` reads no sink and no tracker: a page request should not spend the human's credentials or wait on the network, so it shows what this machine already holds.

A file cannot tell a quiet run from a stopped one by itself, since nothing rewrites it when the Chief of Staff stops. So the page carries the time of the last Run Event and the heartbeat interval, and checks them against the browser's clock: a page left open goes stale on its own. Two intervals, not one, is the line, because a heartbeat that is a minute late is not a stopped Chief of Staff, and a warning that cries wolf is ignored.

The board reads only the run folder and is never hosted, because the drawer shows the Activity Logs, and a log can quote issue text and command output the human has not chosen to publish. A hosted board would be an upload and would need the disclosure and the opt-in every upload has, so it does not exist. For the same reason, a Team Run's board links to the Shared Board rather than copying it: teammates' state has one source, and it is the one they already read. It shares the dashboard's shell and stylesheet, so the two pages look like one tool, and colour means `cause` on both. The board is read-only: a verdict, an answer or a start is a message in the chat, so there is one place the Chief of Staff listens.

## Seams

The config reader checks each top-level key with its own function in one table, `SECTIONS`. A mode that needs keys of its own adds its section there, and its own reference file beside SKILL.md, loaded only when that mode is invoked, as spec mode adds `spec` and SPEC.md. An argument this version does not know stops the run before anything is read, so a newer invocation never runs on an older skill as if it were a set of issues.
