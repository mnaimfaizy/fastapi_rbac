## Verbs

- `spawn`: start a new session with `start_session`, the brief as its first message, in its own worktree, with the plan's model and `permission_mode` set to the Chief of Staff's own mode, so that messages between them are not held (seen in the spec-314 run). The handle is the session's `local_…` id; record it on the board together with the session's name as `ListAgents` prints it (its title), which `notify_when_idle` needs. On a turn the app started rather than the human (a heartbeat firing, an idle notice, a session's turn-end), `start_session` with initiation `user_asked` is refused (seen in the spec-314 run). The refusal covers a background command's completion notice too, even when the human answered an `AskUserQuestion` inside that turn: the answer is not the human's own turn. A session's turn-end that follows straight after the human's own turn, with only other such turn-ends between, may still start one (seen in the spec-344 run). Otherwise, propose the session as an `own_initiative` card instead, with the same `permission_mode`, model and worktree. Until the human starts it with a click, the row is `waiting`, on the open Decision Request "start the card", with the card's task id in its handle cell: a `waiting` row is one SKILL.md step 6 checks on every wake-up, so the card is never left unwatched as `planned` would be. A card keeps `permission_mode`: every card the human started in that run ran in the Chief of Staff's mode, and took messages (seen in the spec-314 run). It does not keep `source_branch` (seen in the spec-314 run), so its brief tells the session to `git switch` to the branch the Chief of Staff cut for it before anything else. The started card's `local_…` id is in the session tools' list of linked sessions (`list_sessions` with `linked: true`), which `ListAgents` does not give (seen in the spec-344 run). The next turn that finds the card's session (any wake-up or heartbeat) records its handle and name in place of the task id, checks its permission mode before the first `message`, sets the row to `running`, and arms its `notify_when_idle` subscription.
- `message`: send a message with `SendMessage` to the session's `local_…` id, which a plain message takes (seen in the spec-314 run). A message to an idle Delegation starts a turn in it (seen in the spec-344 run). A message is held, not delivered, when the two sessions are in different permission-mode classes (one bypasses permission prompts and the other does not) and the receiving session does not accept inbound messages (`crossSessionInbound`). The desktop app cannot show that dialog, so a held message is always dropped after about five minutes, whether or not the human is there. So before the first `message`, check which permission mode the Chief of Staff and each Delegation run in. The Dispatch Plan says whether messages between them would be held, and how the run avoids it: each Delegation started in the Chief of Staff's class where the app allows it, or the human's yes to accepting inbound messages, a persistent change.
- `await`: end the turn, with three things armed. The first wake-up of the three to come starts the next turn:
  1. **The app's own wake-up.** The app continues the idle Chief of Staff once a session it started, and any sibling still working, has ended its turn, quoting the start of the latest report. Each turn-end does this, not only the first (seen in the spec-314 run). This is a turn-end, not a final report.
  2. **A `notify_when_idle` subscription** on each running Delegation: `SendMessage` with `notify_when_idle: true` and no message, which costs that session nothing. Address it to the session's name as `ListAgents` prints it (its title), not its `local_…` id, which the subscription refuses (seen in the spec-314 run). Its notice starts a turn in the idle Chief of Staff (seen in the spec-314 run). It is one notice, so arm it at `spawn` (on the card path, on the turn that finds the started session) and again on a wake-up that finds that Delegation's report not final while the session is still working (a report that says `Final: no, waiting on <background work>` from an idle session is not that case: see below). A subscription armed on a session that is already idle fires at once (seen in the spec-314 run), so never re-arm it on one: that only loops.
  3. **The heartbeat:** one recurring `CronCreate` task in the Chief of Staff's session, `*/10 * * * *` by default (every 10 minutes, starting up to 5 minutes late). Its prompt is plain text that says what each firing does (SKILL.md step 6), including, on this harness, looking in `ListAgents` for the session of each row still waiting on a card, never `/orchestrate`, which a scheduled task cannot invoke because the skill is invoked only by the human. A recurring task expires after 7 days, so recreate it before then and record the new id on the board. Its id is what `CronDelete` takes at close-out.

  A wait on CI or the review is a capped background command, such as a loop on `gh pr checks` or `gh run watch` with its own time limit. It starts a turn when it exits. On macOS there is no `timeout` command, so give the loop its own count of tries rather than wrapping it in `timeout` (seen in the spec-344 run).

  A turn-end whose report says `Final: no, waiting on <background work>` needs no `notify_when_idle` re-arm: the session's next turn-end wakes the Chief of Staff anyway, and the heartbeat covers a stall. A subscription re-armed on that idle session fires at once, and each early turn-end then adds a duplicate notice (seen in the spec-413 run). The brief tells a Delegation to run its re-gate and review sub-agents in the foreground, so this turn-end is the exception, not the pace ([BRIEF.md](../BRIEF.md#the-brief-contract)).

  A turn-end can wake the Chief of Staff twice: once by the app's wake-up, and again later by that turn's `notify_when_idle` notice. Check the second as any wake-up, and log it; when nothing has changed since, it needs no other action (seen in the spec-344 run). A wait that ends with nothing found is re-armed by that turn or, failing that, by the next heartbeat. It is never left ended.

- `report`: the session's report file, and its final message. A Delegation's Write tool may refuse a path outside its worktree, such as the run folder. It then writes `report.md` and `activity.md` with the shell, to the same absolute paths (seen in the spec-344 run). A Delegation can end a turn while its own background re-gate or review agents still run, with no report written. It did so even though its brief forbade it, until the `spawn` message repeated the rule: "first write `report.md` with `**Final:** no, waiting on <what>`" (seen in the spec-344 run). So the `spawn` message repeats that rule.
- A sub-agent, for an analysis Delegation: the in-session agent tool. Its result returns to the Chief of Staff when it finishes.
- A QA Delegation: start the session on its brief, and once its first phase has stopped, `message` it `/qa-plan <n> [--answers <working_dir>/qa-readiness.json]`; later, `/manual-qa <plan file>`. With `go`, that is the typed route; with `go autonomous`, on a `stack` or a `url` target, the same session follows its brief instead, reading each QA skill's `SKILL.md` from the paths the brief gives, so no command is sent or typed. A `url` target runs from the brief too, with its hosts typed in the Dispatch Plan and relayed through the brief.
- Parked QA sessions: with QA approved in the Dispatch Plan (SKILL.md step 4), start one Live Session per QA row on the `go` turn, with `start_session` and initiation `user_asked`: the human's words on that turn authorize it, as for any session started at `go`. Each gets its own worktree, the plan's model and `permission_mode` as in `spawn`, and a QA brief written without `<head>` ([BRIEF.md](../BRIEF.md#the-qa-brief)). It stays idle until messaged the head to pin. Record its `local_…` id and name on the board with the row `parked`, and arm no `notify_when_idle` subscription on it: an idle session has nothing to report, and a subscription armed on an idle session fires at once. When SKILL.md step 9 has a verified head for the row, `message` the session the head, the pull request and the paths of the answers files, once no other holder of the QA Stack is running, then set the row `running` and arm the subscription as for `spawn`. The QA Stack is still held by one session at a time: parked sessions hold nothing, and the Chief of Staff messages one holder at a time. No source says a `start_session` call for work whose input arrives later is refused or allowed to idle for hours; the first run to use it records what it saw (**Check before use**).
- Re-QA in a parked session: a re-QA is a new QA Delegation (`d<issue>-qa2`, then `-qa3`) on the board, with its own row, but it runs in the same session as the QA Delegation before it. Before the message, the Chief of Staff checks that the earlier QA Plan and QA Report are copied to the run folder, since the session throws away its old state. The message names the new head and says it is a re-QA: the session throws away its old state (detached head, `<working_dir>` files, answers copies; any QA Stack it started stopped) and re-pins the new head, then composes a plan again ([BRIEF.md](../BRIEF.md#the-qa-brief)). The earlier row stays on the board, `void` or `failed`, with the same handle.
- An unusable parked session: a parked session that was archived, crashed or dropped (a `message` that finds no session, or an error the Chief of Staff cannot clear) holds its row for close-out: set the row `waiting`, list it in `qa-held.md` with the session's id and what the Chief of Staff saw, and go on with the other rows. Nothing replaces it mid-run, since no card is ever started mid-run: a card needs the human's click, which an unattended run does not have, and the run stalls at it (Limits). At close-out the human may start a session for the row on its head by hand.
- This harness may also run the Claude Code CLI's headless runs ([claude-code-cli.md](claude-code-cli.md)).

## Limits

- QA skills: a slash command sent as a message may not run as the human's own invocation. In the first run (2026-11-13), the QA session could not invoke `qa-plan` itself, and the human typed `/qa-plan <n>` there.
- The app's wake-up waits for sibling sessions still working. With two Delegations running, a short one's report may wait behind a long one, until the heartbeat or its `notify_when_idle` notice comes. Which sessions count as siblings is a check before use item.
- A Delegation stopped on a permission prompt wakes nobody: it has not ended its turn, and it is not idle. The heartbeat finds it as no sign of progress (SKILL.md step 6).
- A `notify_when_idle` subscription is dropped after 12 hours.
- Machine sleep stops every timer: the heartbeat, the capped waits and the app's own wake-ups. A closed lid still sleeps. For a run left unattended, the Dispatch Plan tells the human to turn on **Keep computer awake** (in **Settings > Desktop app**). Changing the setting is the human's to do.
- Every heartbeat firing is a short turn on the Chief of Staff's model over its whole context. A firing with nothing new logs one line and ends.
- A Delegation in `auto` permission mode may be refused writes to the tracker. In the spec-344 run, its permission check refused `gh api -X POST …/pulls/<n>/comments/<id>/replies`, a reply on its own review, before the call ran. Never ask it to retry around the refusal: the Chief of Staff posts the drafted replies itself, as writes as the human, on the human's yes (seen in the spec-344 run).
- Outside an approved-QA run's parked QA sessions, most of a run's sessions may start from cards, so each needs the human's click. Each turn the app starts (a heartbeat, a turn-end, an idle notice) can only propose the next wave's session (seen in the spec-344 run: five of seven). An unattended run therefore stalls at each wave until the human clicks. The Dispatch Plan says so under **Harness limits**.
- In `auto` mode, `archive_session` is first refused once: a hook adds a `session` field after the classifier reviewed the call. Sending the call again with exactly the input the refusal quotes goes through (seen in the spec-344 run).

## Check before use

- Whether a QA session accepts a host relayed through its brief: that it checks it again with `adapter.mjs host` before any sign-in, and holds its scenarios (never asks) when it refuses it. A harness whose session does not holds every scenario of a `url` target. Record what was found.
- How long an idle parked QA session stays usable: whether the app ends, archives or drops a session left idle for hours (in spec-253, a QA session started about a day after `go`), and whether a `message` to it then starts a turn (not yet confirmed).
- Re-pinning a voided session: whether a QA session that has run once, sent a re-QA message, throws away its old state and re-pins cleanly, with `qa-plan` and `manual-qa` coping with a second pass in one session (not yet confirmed).
- What "any sibling still working" covers in the app's wake-up: every session the Chief of Staff started, or only those started together (not yet confirmed).
- Whether a message that reaches the Chief of Staff as its own turn ends starts a new turn (not yet confirmed).
- That a session-scoped `CronCreate` task fires while the app is in the background or minimised (not yet confirmed; likely, since the session keeps running).
- Whether a sub-agent can be sent a follow-up message after it finishes.
- Whether the app runs a slash command sent as a message as the user's own invocation. Try it; if the session does not run it, the human types it. Record which happened.
- Whether a `PushNotification` reaches the human when the app is in the background or closed.
