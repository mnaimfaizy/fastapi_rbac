## Verbs

- `spawn`: start a new session with `start_session`, the brief as its first message, in its own worktree, with the plan's model and `permission_mode` set to the Chief of Staff's own mode, so that messages between them are not held (seen in the spec-314 run). The handle is the session's `local_…` id; record it on the board together with the session's name as `ListAgents` prints it (its title), which `notify_when_idle` needs. On a turn the app started rather than the human (a heartbeat firing, an idle notice, a session's turn-end), `start_session` with initiation `user_asked` is refused (seen in the spec-314 run): propose the session as an `own_initiative` card instead, with the same `permission_mode`, model and worktree. Until the human starts it with a click, the row is `waiting`, on the open Decision Request "start the card", with the card's task id in its handle cell: a `waiting` row is one SKILL.md step 6 checks on every wake-up, so the card is never left unwatched as `planned` would be. A card keeps `permission_mode`: every card the human started in that run ran in the Chief of Staff's mode, and took messages (seen in the spec-314 run). It does not keep `source_branch` (seen in the spec-314 run), so its brief tells the session to `git switch` to the branch the Chief of Staff cut for it before anything else. The next turn that finds the card's session in `ListAgents` (any wake-up or heartbeat) records its handle and name in place of the task id, checks its permission mode before the first `message`, sets the row to `running`, and arms its `notify_when_idle` subscription.
- `message`: send a message with `SendMessage` to the session's `local_…` id, which a plain message takes (seen in the spec-314 run). A message is held, not delivered, when the two sessions are in different permission-mode classes (one bypasses permission prompts and the other does not) and the receiving session does not accept inbound messages (`crossSessionInbound`). The desktop app cannot show that dialog, so a held message is always dropped after about five minutes, whether or not the human is there. So before the first `message`, check which permission mode the Chief of Staff and each Delegation run in. The Dispatch Plan says whether messages between them would be held, and how the run avoids it: each Delegation started in the Chief of Staff's class where the app allows it, or the human's yes to accepting inbound messages, a persistent change.
- `await`: end the turn, with three things armed. The first wake-up of the three to come starts the next turn:
  1. **The app's own wake-up.** The app continues the idle Chief of Staff once a session it started, and any sibling still working, has ended its turn, quoting the start of the latest report. Each turn-end does this, not only the first (seen in the spec-314 run). This is a turn-end, not a final report.
  2. **A `notify_when_idle` subscription** on each running Delegation: `SendMessage` with `notify_when_idle: true` and no message, which costs that session nothing. Address it to the session's name as `ListAgents` prints it (its title), not its `local_…` id, which the subscription refuses (seen in the spec-314 run). Its notice starts a turn in the idle Chief of Staff (seen in the spec-314 run). It is one notice, so arm it at `spawn` (on the card path, on the turn that finds the started session) and again on a wake-up that finds that Delegation's report not final while the session is still working. A subscription armed on a session that is already idle fires at once (seen in the spec-314 run), so never re-arm it on one: that only loops.
  3. **The heartbeat:** one recurring `CronCreate` task in the Chief of Staff's session, `*/10 * * * *` by default (every 10 minutes, starting up to 5 minutes late). Its prompt is plain text that says what each firing does (SKILL.md step 6), including, on this harness, looking in `ListAgents` for the session of each row still waiting on a card, never `/orchestrate`, which a scheduled task cannot invoke because the skill is invoked only by the human. A recurring task expires after 7 days, so recreate it before then and record the new id on the board. Its id is what `CronDelete` takes at close-out.

  A wait on CI or the review is a capped background command, such as a loop on `gh pr checks` or `gh run watch` with its own time limit. It starts a turn when it exits. A wait that ends with nothing found is re-armed by that turn or, failing that, by the next heartbeat. It is never left ended.

- `report`: the session's report file, and its final message.
- A sub-agent, for an analysis Delegation: the in-session agent tool. Its result returns to the Chief of Staff when it finishes.
- A QA Delegation: start the session on its brief, and once its first phase has stopped, `message` it `/qa-plan <n> [--answers <working_dir>/qa-readiness.json]`; later, `/manual-qa <plan file>`. With `go`, that is the typed route; with `go autonomous`, on a `stack` target, the same session follows its brief instead, reading each QA skill's `SKILL.md` from the paths the brief gives, so no command is sent or typed. A `url` target stays on the typed route.
- This harness may also run the Claude Code CLI's headless runs ([claude-code-cli.md](claude-code-cli.md)).

## Limits

- QA skills: a slash command sent as a message may not run as the human's own invocation. In the first run (2026-11-13), the QA session could not invoke `qa-plan` itself, and the human typed `/qa-plan <n>` there.
- The app's wake-up waits for sibling sessions still working. With two Delegations running, a short one's report may wait behind a long one, until the heartbeat or its `notify_when_idle` notice comes. Which sessions count as siblings is a check before use item.
- A Delegation stopped on a permission prompt wakes nobody: it has not ended its turn, and it is not idle. The heartbeat finds it as no sign of progress (SKILL.md step 6).
- A `notify_when_idle` subscription is dropped after 12 hours.
- Machine sleep stops every timer: the heartbeat, the capped waits and the app's own wake-ups. A closed lid still sleeps. For a run left unattended, the Dispatch Plan tells the human to turn on **Keep computer awake** (in **Settings > Desktop app**). Changing the setting is the human's to do.
- Every heartbeat firing is a short turn on the Chief of Staff's model over its whole context. A firing with nothing new logs one line and ends.

## Check before use

- What "any sibling still working" covers in the app's wake-up: every session the Chief of Staff started, or only those started together (not yet confirmed).
- Whether a message that reaches the Chief of Staff as its own turn ends starts a new turn (not yet confirmed).
- That a session-scoped `CronCreate` task fires while the app is in the background or minimised (not yet confirmed; likely, since the session keeps running).
- Whether a sub-agent can be sent a follow-up message after it finishes.
- Whether the app runs a slash command sent as a message as the user's own invocation. Try it; if the session does not run it, the human types it. Record which happened.
- Whether a `PushNotification` reaches the human when the app is in the background or closed.
