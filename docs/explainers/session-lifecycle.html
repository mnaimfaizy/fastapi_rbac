Session lifecycle, run on the live system

When a token is issued, used, refreshed or revoked: which Redis allowlist entries change, which other sessions survive, and what does the SPA do with the response?

    What each part of the stage holds

    • Browser · SPA: memory holds the access token (module memory only); localStorage holds the non-secret auth_session_active hint; the cookie jar holds refresh_token (HttpOnly, Path=/api/v1/auth) and fastapi-csrf-token. The tabs switch between this user's devices. (tokenStorage.ts:16-38; auth_cookies.py:12-55; auth.py:1783-1810)
    • HTTP edge: what a request meets before its route body runs. The client address is read from forwarded headers only when the socket peer is a trusted proxy; the CSRF dependency compares X-CSRF-Token with the signed fastapi-csrf-token cookie; login is rate-limited to 5/minute. (client_address.py:139-166; main.py:217-221; deps.py:212-229; auth.py:78)
    • API · FastAPI: the auth routes and the get_current_user dependency. The lit socket is what is running; the list under it is the checks it has passed, in order. (deps.py:66-130; auth.py as cited per beat)
    • Redis: per user, the sorted sets user:{id}:refresh_token and user:{id}:access_token, each with a :meta hash, drawn grouped by session_id (letter and device). The meter counts live refresh entries against the cap. Outside testing, slowapi's rate-limit counters live here too. (token.py:26-48; rate_limit.py:69-79)
    • Postgres: the User row (password hash, is_active, verified, is_locked, number_of_failed_attempts, needs_to_change_password) and the AuditLog rows that log_security_event appends. (user_model.py:20-49; background_tasks.py:174-188, :195-228)
    • refresh entry (square corners)
    • access entry (round)
    • request (filled, pointed)
    • response (outlined)
    • 2xx · 401 (expired: refresh) · 403 (refused: no refresh)
    • expired, evicted, revoked or ended (✕, hatched)

    The reading test for a PR reviewer

    If your change writes an allowlist entry without a session_id in its :meta entry, POST /logout cannot find it. That token outlives logout until its JWT expires. If your change adds a path that mints tokens, name which session it joins.

    Locate the change on the stage: which key it writes in the Redis zone, which session_id its meta carries, and whether it is a refresh add (which counts toward the cap and records an origin) or an access add (which does neither).

    R1

    The allowlist at a glance
    • Each user has two expiry-scored Redis sorted sets, one for refresh tokens and one for access tokens.
    • Each set has a :meta hash: field = the token, value = JSON {issued_at, exp, session_id, origin_ip}.
    • Key names, verbatim: user:{user_id}:refresh_token, user:{user_id}:refresh_token:meta, user:{user_id}:access_token, user:{user_id}:access_token:meta.
    • Tokens are grouped into sessions by session_id = sha256(refresh_token).hexdigest().
    • The allowlist holds exactly three token types under this key shape: access_token, refresh_token, reset_token. Reset keys are not drawn. Email verification uses verification_token:{id} and is not part of the allowlist.

    Diagram notes

    The text behind each ⓘ shape in the diagram.

    • user:{user_id}:refresh_token — sorted set. Member: the refresh JWT. Score: its absolute expiry, issued_at + expire_minutes*60. Expired members (score ≤ now) are purged with their meta fields on every add and on every read through get_valid_tokens. After each add, the key's TTL is set to the latest member expiry. Adding here is the only thing that enforces the concurrent-session cap. (token.py:51-72, :219-226, :238-239)
    • user:{user_id}:refresh_token:meta — hash. Field: the token. Value: JSON {issued_at, exp, session_id, origin_ip}, empty string when unset. A refresh entry gets session_id = sha256(refresh_token) by default when none is passed. (token.py:38-48, :221-222, :227-236)
    • user:{user_id}:access_token — sorted set, scored by expiry. get_current_user checks membership here on every authenticated request; a token missing from it gets 403 even though its JWT still decodes. (backend/app/api/deps.py:101-106)
    • user:{user_id}:access_token:meta — hash, same JSON shape. Its session_id is how logout, eviction and origin-anomaly revocation find an access token's session. origin_ip is always empty here. (token.py:136-151, :166-188, :264-280)
    • Session A: one session_id — sha256(refresh_token).hexdigest(). The refresh entry and every access token minted from it carry the same value: add_session_tokens_to_redis at login, add_derived_access_token_to_redis at refresh. (token.py:21-23, :263-298)
    • origin_ip — the full client address from get_client_ip at login, stored on the refresh entry only. It is compared at network granularity, at refresh only, when VALIDATE_TOKEN_IP is on. (token.py:126-133, :257-261)
    • Session C: form login — POST /api/v1/auth/access-token issues an access token only, with session_id = sha256(access_token). No refresh token, no cookie, no origin. The concurrent-session cap is not consulted, because only refresh adds enforce it. (auth.py:1111-1119, :1262-1272)

    R5

    The origin-network rule
    • The check runs at refresh only. Access tokens are never checked against the origin (token.py:126-128).
    • It is gated by VALIDATE_TOKEN_IP, default true (token.py:130-133; config.py:329).
    • The origin is the full client address, stored on the refresh entry only, and compared by network.
    • IPv4 addresses are compared as /24 networks, IPv6 as /64 (origin_network.py:21-22).
    • IPv4-mapped IPv6 is normalised to IPv4 first (origin_network.py:43-44).
    • A missing or unparseable address on either side is not a mismatch (origin_network.py:63-80).
    • IPv4 against IPv6 is a mismatch (origin_network.py:70-75, :81).
    • A mismatch revokes that one session and answers like an invalid token (R2, row 6).
    • The compared address has one reader, get_client_ip, which returns request.client.host (client_address.py:158-166).
    • ProxyHeadersMiddleware corrects that value once. It is registered last, so it is the outermost middleware (backend/app/main.py:217-221).
    • Forwarded headers count only when the socket peer is in TRUSTED_PROXIES. Then X-Forwarded-For is read right to left past trusted proxies, then X-Real-IP, else the peer (client_address.py:139-155).
    • Wildcard and /0 entries in TRUSTED_PROXIES are refused at settings load (client_address.py:86-100).

    Two different things called refresh_token

    The cookie name
    refresh_token
    Comes from the setting REFRESH_TOKEN_COOKIE_NAME. It is what the browser stores and sends to /api/v1/auth.
    The Redis key segment
    user:{user_id}:refresh_token
    The token_type segment: the TokenType.REFRESH enum value. It names a sorted set, not a cookie.

    They are spelled the same by default and set in different places. Renaming the cookie does not rename the key, and the reverse.
